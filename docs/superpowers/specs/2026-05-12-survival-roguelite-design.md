# 生存向 Web Roguelite — 设计说明

**日期：** 2026-05-12  
**状态：** 已定稿（待实现计划）  
**范围：** 尽量简单的浏览器小游戏，带 Roguelike 元素（随机、单局、无局外养成第一版）。

---

## 1. 背景与目标

在空仓库上从零实现一款**生存式**小游戏：以**有限资源压力**和**随机事件**为主，玩家尽量延长存活。优先**规则少、可快速做完、易部署**，不引入后端与账号系统。

**成功标准：**

- 单局可在数分钟内玩多步，事件文本可读、反馈清晰。
- 每局因随机事件序列不同而有重玩价值。
- 纯静态前端即可运行（本地或任意静态托管）。

**非目标（第一版不做）：**

- 大地图探索、复杂战斗演算、局外 meta 养成、存档云同步、多人联机。

---

## 2. 核心玩法

### 2.1 资源与结束条件

- **单一主资源「生存值」**：有上限（例如 100），显示为一条数值或进度条。
- **生存值 ≤ 0**：本局 **Game Over**，展示本局分数后仅允许「再来一局」类操作。
- **无硬性胜利条件**：分数 = **存活完整天数 `day`**（见第 5 节「天数规则」）。生存值变化仅由事件引起。

### 2.2 回合结构

1. 玩家触发 **「进行下一天」**（或「下回合」）。
2. 从 **事件池** 中按 **加权随机** 抽取一条事件。
3. 应用事件对生存值的修改（及日志文案）；将生存值限制在 `[0, maxSurvival]`。
4. 事件结算后：若 `survival > 0`，则 `day += 1` 并允许继续；若 `survival <= 0`，则进入 Game Over（`day` 不增加）。详见第 5 节。

### 2.3 事件设计

- 第一版事件数量控制在 **8～12 条**。
- 类型示例：**小幅恢复**、**小幅伤害**、**高风险高回报的二选一**、**无事发生**。部分事件可弹出 **1～2 个按钮** 供玩家选择；其余事件自动结算。
- **Roguelike 感**：事件池固定内容，但每局 **顺序与随机性** 不同；权重可随天数略调（可选增强，**第一版可省略**，仅均匀或简单加权即可）。

### 2.4 局外与存档

- **第一版无局外养成**；刷新页面视为新局。
- **可选后续增强**：可重复随机种子（URL 参数或「复制种子」）；**第一版不实现 seed**，以降低工作量。

---

## 3. 用户界面（最小集）

- **生存值**与**当前天数**始终可见。
- **事件日志**：保留最近若干条（例如 5～10 条），新事件追加、旧的可丢弃或折叠（实现任选其一，以简单为准）。
- **主按钮**：「进行下一天」；Game Over 后该按钮禁用或替换为「再来一局」（重置状态）。
- 需要玩家选择时：在日志区下方或模态区域展示 **2 个以内** 的选项按钮。

视觉风格无硬性要求；以默认系统字体与清晰布局即可。

---

## 4. 技术方案

### 4.1 推荐栈

- **Vite + TypeScript**，代码拆为少量模块（非单文件巨石），便于测试与扩展。
- **纯前端**：无 API、无数据库；状态仅存内存。

### 4.2 备选

若强烈追求零构建，可退化为 **单 HTML + 单 JS**；玩法与本规格一致，仅工程形态不同。

### 4.3 模块边界

| 模块 | 职责 |
|------|------|
| `events` | 事件表定义、类型（自动 / 需选择）、效果描述与数值变更 |
| `engine` | 持有局内状态、推进一天、应用事件结果、判定结束；**纯逻辑优先**，便于单测 |
| `ui` | 绑定 DOM（或极简组件）展示状态、处理点击、调用 engine |

随机数：使用 `Math.random` 即可第一版；若日后加 seed，再封装 RNG。

## 5. 状态模型

建议最小状态：

```ts
type GamePhase = "playing" | "gameover";

interface GameState {
  phase: GamePhase;
  survival: number;      // 当前生存值
  maxSurvival: number;   // 上限
  day: number;           // 已成功存活的天数（仅在本步结算后 survival > 0 时递增）
  log: string[];         // 最近日志，长度有上限
}
```

**天数规则（定稿）：** 玩家触发「进行下一天」并完成该步事件结算后：若 `survival > 0`，则 `day += 1`；若 `survival <= 0`，则 `phase = "gameover"`，且 **`day` 不增加**。本局 **分数 = `day`**。日志须记录本步事件文案（含致死步）。

---

## 6. 边界与错误处理

- 生存值 **clamp** 到 `[0, maxSurvival]`，禁止显示负数或超上限。
- `phase === "gameover"` 时禁止再次推进，仅允许重置新局。
- 若事件需要选择而玩家未选（不应出现）：引擎不应推进；UI 在展示选项时禁用「下一天」主按钮直到选择完成（二选一事件可先选再自动结算该步）。

---

## 7. 测试策略

- 为 `engine` 编写单元测试：注入**固定随机序列**（或通过可注入的 `() => number`）与固定事件队列，断言状态迁移与日志片段。
- UI 层第一版可不做 E2E，手动烟测即可。
